# สถานะก่อนนำระบบขึ้น staging — 2 ตุลาคม 2026

งานแก้ไขและการทดสอบที่ทำได้ในเครื่องเสร็จแล้ว พร้อมเข้าสู่ขั้นเผยแพร่ image และตั้ง staging บน Coolify ยังต้องตรวจค่าตั้งและ Gateway จริงก่อนเปิดรับข้อมูล pilot และยังไม่รับรองความสามารถรองรับข้อมูลเต็มขนาด

ผลล่าสุด: สร้าง image ครบ 6 ส่วน; lint/unit, CI script tests 12 รายการ, regression 87 รายการ, browser/E2E ทุกบทบาท, managed MQTT, staging Compose และซ้อมกู้คืนผ่านแล้ว โหลดขนาดเล็ก 5 ผู้ใช้เปิดหน้า 80 ครั้ง ไม่มี error และทุกครั้งต่ำกว่า 2 วินาที ดู [หลักฐานและข้อจำกัด](../performance/platform-validation-2026-10-02.md)

ผู้ใช้แจ้งว่าทดสอบ Aglowthai เสร็จแล้ว เมื่อตรวจอีกครั้งไม่มี container รันอยู่ จึงไม่ต้องหยุดบริการของโปรเจกต์อื่น ผู้ใช้อนุมัติให้ commit/push branch งานแล้ว ส่วน merge และ deploy เป็นขั้นตอนถัดไป

## ขอบเขตที่ผู้ใช้ยืนยัน

- ใช้ `solar.fowir.com` และ `mqtt-solar.fowir.com` รับข้อมูลผ่าน MQTT
- เริ่ม pilot หนึ่ง Gateway แล้วตรวจเส้นทางรับข้อมูล บันทึก และแสดงผล พร้อมทดสอบทุกบทบาท
- แยกฐานข้อมูลและ broker ของ E2E จาก staging ที่เก็บข้อมูลจริงต่อเนื่อง
- ยังไม่รวมข้อเสนอระบบการเงิน F2 และยังไม่เปิดการอนุมัติหรือออกเอกสารการเงินจริง
- เครื่องบริษัท 2 CPU / RAM 4 GB ใช้สำหรับ pilot; การทดสอบโหลดเต็มขนาดต้องใช้เครื่องแยก

## งานที่ทำในโค้ดแล้ว

| ส่วน | สิ่งที่ปรับ | ผลทดสอบในเครื่อง / งานบนสภาพแวดล้อมจริง |
|---|---|---|
| Dashboard และรายงาน | หน่วยกำลังไฟฟ้า ข้อมูลขาดหาย สถานะความสด การใช้คีย์บอร์ด และการกลับมาออนไลน์ | Browser tests จาก image ชุดสุดท้ายผ่าน |
| ข้อมูลย้อนหลัง | Archive แบบไม่เขียนทับ ตรวจ checksum ตรวจสิทธิ์ซ้ำ และสั่งกู้ข้อมูลผ่านงานเบื้องหลัง | Archive 8 tests และ browser ทั้งเปิด/ปิดบริการผ่าน; SLA ขนาดคำขอจริงยังต้องวัด |
| สำรองและกู้คืน | PostgreSQL backup/WAL, สถานะระหว่าง backup, การเข้ารหัสไฟล์ และตรวจเอกสารที่ฐานข้อมูลอ้างถึง | ซ้อมกู้และหยุด backup 191 วินาทีผ่าน; ยังต้องทดสอบนอกเครื่องจริง |
| Monitoring | แจ้งเตือนแบบเก็บสถานะ ป้องกันส่งซ้ำ และตรวจหลักฐานให้ตรง revision/image/config | Endpoint, webhook fixture และ Compose ผ่าน; ผู้รับแจ้งเตือนจริงยังต้องยืนยัน |
| ประสิทธิภาพ | เตรียม workload, การส่งซ้ำ, รายงานสองงาน และวัดเวลาหน้าเว็บ | Smoke ผ่าน; ยังต้องวัดเต็มขนาด รวม cold DB และรายงานใหญ่ทำงานซ้อนกัน |

การตรวจโค้ดพบและแก้เพิ่มเติมแล้ว: retry งานกู้ข้อมูลเมื่อบริการปิด, worker แย่งงานกับ test fixture, advisory lock ของ monitoring ชนกับ archive และปลายทางไฟล์ของ worker ไม่ตรง API

## สิ่งที่ต้องใช้ staging หรือข้อมูลจากภายนอก

ก่อนเริ่มขั้นตอนด้านล่าง ต้อง commit/merge โค้ดตามกระบวนการทีม และให้ CI สร้าง ทดสอบ และเผยแพร่ image จาก `main` แล้วใช้ registry digest จาก CI ตั้งใน Coolify การ commit/push branch งานไม่แทนผล CI ของ main และยังไม่ใช่การ merge หรือ deploy

1. ยืนยัน DNS, TLS, เส้นทาง proxy และ CIDR ที่เชื่อถือได้บน Coolify จริง
2. ให้ Gateway ยืนยันรูปแบบข้อมูล และทดสอบส่งซ้ำหลังขาดการเชื่อมต่อ ก่อนอนุญาต deploy ระหว่างรับข้อมูลจริง
3. กำหนดปลายทาง backup นอกเครื่อง เก็บกุญแจกู้คืน และซ้อมกู้บนโฮสต์อิสระ เป้าหมาย 4 ชั่วโมง / สูญข้อมูลไม่เกิน 15 นาทียังไม่ได้รับการพิสูจน์
4. วัดข้อมูล 100 โรงเรียน / 1,000 มิเตอร์ / ผู้ใช้พร้อมกัน 50 คน รวมกรณีฐานข้อมูลยังไม่มี cache โดยหน้าใช้งานต้องผ่านเกณฑ์ 2 วินาทีที่ตกลง
5. ตกลงขนาดคำขอกู้ข้อมูลย้อนหลังที่จะรับรองภายใน 1 ชั่วโมง แล้วทดสอบตามขนาดนั้น
6. ตรวจการใช้งานด้วย screen reader และการซูมจริงเพิ่มเติม ผล automated accessibility ไม่ใช่การรับรอง WCAG ทั้งระบบ

ยังปิดการลบข้อมูลดิบไว้ แม้มี archive แล้ว เพราะต้องพิสูจน์ว่าข้อมูลทุกแถว รวมข้อมูลมาช้าหรือแก้ย้อนหลัง มีหลักฐานเก็บครบก่อน การมี catalog ครอบคลุมช่วงเวลาอย่างเดียวไม่เพียงพอ
