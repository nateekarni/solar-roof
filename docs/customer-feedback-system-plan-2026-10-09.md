# แผนปรับปรุงระบบจากฟีดแบคลูกค้า — 9 ตุลาคม 2569

สถานะ: ร่างระหว่างสัมภาษณ์ด้วย grill-with-docs ยังไม่ใช่ข้อกำหนดที่อนุมัติหรือคำสั่งให้ลงมือแก้ระบบ

เอกสารนี้เป็นบันทึกสัมภาษณ์และข้อเสนอเดิมตามลำดับเวลา ใช้คำตอบล่าสุดแทนข้อความก่อนหน้าที่ขัดกัน แบบระบบที่รวบรวมเป็นฉบับเดียวสำหรับตรวจยืนยันอยู่ที่ `docs/superpowers/specs/2026-10-09-customer-feedback-system-design.md` ผลศึกษา OCR อยู่ที่ `docs/ocr-local-feasibility-2026-10-09.md`

## การปรับขอบเขตล่าสุด: ตัด OCR และลดข้อมูลลูกค้าต้องกรอก

ผู้ใช้ขอเอา OCR ออกและเน้นแนบหลักฐานอย่างสะดวก ข้อเสนอแบบระบบล่าสุด: บังคับเฉพาะไฟล์หลักฐาน มีหมายเหตุไม่บังคับ; บิล/ลูกค้า/ไซต์/ผู้ส่ง/เวลาส่งมาจากระบบ ไม่มีฟอร์มยอด/เวลา/ธนาคาร/ชื่อผู้โอน/เลขอ้างอิงที่บังคับลูกค้ากรอก เจ้าหน้าที่อ่านและยืนยันยอดโอน/วันเวลาโอนก่อนอนุมัติ; เลขอ้างอิงและข้อมูลธนาคารเพิ่มได้ตามจำเป็น ไม่ใช้ยอดบิลแทนยอดโอนหรือเวลาส่งแทนเวลาโอน แยก evidence submission จาก verified transfer values ใน API/schema/DTO/ยอดรวม และตรวจรับ flow แนบไฟล์แล้วส่งโดยไม่กรอกข้อมูลอื่น ข้อนี้แทนข้อเสนอ OCR และฟอร์มลูกค้าใน Q21/Q23/Q28/Q29 ทั้งหมด

ผู้ใช้ยืนยันว่าเครื่องเดิมใช้ DEMO ส่วน production จะกำหนดตามปริมาณลูกค้าและขยายภายหลัง จึงไม่ต้องตัดสิน production sizing ในการสัมภาษณ์นี้ และไม่ใช้ comment 2 vCPU/4 GiB แทนผลตรวจเครื่องจริง การอ่าน Docker/CIM จาก sandbox ไม่สำเร็จ จึงยังไม่มี hardware inventory ปัจจุบัน

## คำตอบที่ยืนยันรอบแรก — ใช้แทนข้อเสนอที่ขัดกันด้านล่าง

- Q1 ตามคำแนะนำ: Owner จัดการไซต์/ธุรกิจและ Owner/Accountant จัดการการเงิน; Admin จัดการลูกค้า/เกตเวย์/อุปกรณ์และไม่มีสิทธิ์เอกสารที่ UI/API/download; Operator คงหน้าที่เทคนิค
- Q2 ระบบไม่มี workflow ทำสัญญา: เอาเมนูและกระบวนการสัญญาออก ใช้การเพิ่มไซต์โดย Owner และตั้งค่าลูกค้าสำหรับออกเอกสาร เรท การทวงชำระ และค่าเกี่ยวข้องในไซต์ ไม่ใช่เพียงซ่อนเมนูแล้วบังคับสร้างสัญญาอยู่
- Q3 มีตารางเรทกลางในระบบ แล้วเลือกไปปรับใช้แยกรายไซต์; Owner แก้เรทได้เมื่อบิลออกแล้วแต่ยังไม่ชำระ; บันทึกแล้วปิดช่วงเรทเดิมและเพิ่มช่วงเรทใหม่ไม่กำหนดวันสิ้นสุดอัตโนมัติ วันที่มีผลกับการคำนวณบิลที่ออกแล้วต้องถามให้ชัด
- Q4 สร้างแล้วออกทันที ไม่ต้องยืนยันการออกตามปกติ และยังแก้เรทได้ตามเงื่อนไขบิลค้างชำระ; เวลารันยังไม่ได้ตอบโดยตรง
- Q5 กฎแจ้งเตือนกำหนดเงื่อนไขและเลือกผู้รับเป็นรายกฎได้ ผู้รับยังต้องอยู่ในสิทธิ์ข้อมูลตาม Q1; ประเภทเงื่อนไขและค่าเริ่มต้นอยู่ในรอบถัดไป
- Q6 Table/Code แก้เฉพาะรายการข้อมูลได้ทั้งสองด้านและ sync ต่อเนื่อง; JSON ที่ parse ไม่ผ่านคงข้อความไว้โดยไม่ทำลาย structured draft ล่าสุด และห้ามบันทึกจนแก้ให้ถูกต้อง
- Q7 ใช้ template Register ตามรุ่นพร้อม override รายอุปกรณ์; การสั่งอุปกรณ์จริงขึ้นกับ gateway protocol ที่ยืนยัน
- Q8 หนึ่งไซต์งาน = หนึ่งเกตเวย์ โดยอาจมีอุปกรณ์หลายตัวหลังเกตเวย์
- ตรวจ UX ทุกบทบาทและทุกมุมมอง: ตัวแทนลูกค้าเห็นเฉพาะไซต์ที่มีสิทธิ์ ไม่มีปุ่มทุกไซต์; หน้ารายละเอียดและเอกสารมี preview ในหน้า; ดูดีและใช้งานง่าย
- ระบบอยู่ระหว่างพัฒนา ผู้ใช้อนุญาตปรับโครงสร้างและเปลี่ยนของเดิมเพื่อให้ตรงแบบใหม่ ไม่ต้องคง contract workflow เพื่อความเข้ากันได้; ไม่ตีความเป็นอนุญาตล้างฐานข้อมูลหรือข้อมูลเอกสารทั้งหมด

## รูปแบบระบบเป้าหมาย

Owner: หน้าแรก → ไซต์งาน → สร้างไซต์ → เลือกลูกค้า/ข้อมูลออกเอกสาร → ตั้งค่าเรท/รอบบิล/กำหนดชำระ/ทวงชำระ → ติดตามการเงินและเอกสาร

Admin: ข้อมูลลูกค้า → เกตเวย์ → เลือกไซต์ที่ Owner สร้าง → ผูกเกตเวย์หนึ่งตัว → ตั้งรุ่นอุปกรณ์/รายการข้อมูล/Register → ตรวจการเชื่อมต่อและความพร้อมข้อมูล

ตัวแทนลูกค้า: หน้าแรกของไซต์ที่ได้รับสิทธิ์ → การผลิต → เอกสาร/preview → ชำระและแนบหลักฐาน; ไม่มีทุกไซต์หรือการตั้งค่าเทคนิค

ชุดงานเพิ่มเติม: ตัด contract dependency จาก schema/API/calculation/scheduler/recipients/DTO/document templates/fixtures ไม่ใช่แก้ navigation อย่างเดียว; แยกการพร้อมใช้งานเทคนิคจากการพร้อมออกบิล

## UX acceptance เพิ่มเติม

- ตรวจ desktop sidebar, mobile menu, bottom navigation, action buttons, detail pages, empty/loading/error states ตาม role matrix เดียวกัน
- ผู้มีไซต์เดียวเข้าไซต์นั้นทันที; หากอนุญาตหลายไซต์แสดงเฉพาะไซต์ที่ได้รับสิทธิ์ ไม่มี All sites และ API/download ต้องคุม scope เหมือนหน้าจอ
- Owner เห็นค่าธุรกิจและสถานะพร้อมใช้งาน; Admin เห็น gateway/config โดยไม่เห็นยอดเงินหรือเอกสารผ่าน widget/notification ทางอ้อม
- เอกสารที่ออกแล้ว preview จากไฟล์ฉบับจริงในหน้าและดาวน์โหลดฉบับเดียวกัน; เอกสารก่อนออกถ้ามีใช้ตัวอย่างที่ติดป้ายชัด ไม่สร้างเอกสารประวัติขึ้นใหม่จาก config ปัจจุบัน
- หน้ารายละเอียดแบ่งข้อมูลทั่วไป/การผลิต/การเรียกเก็บ/อุปกรณ์ตามสิทธิ์ พร้อม title ลูกค้าและไซต์ชัดเจน

## ข้อรอตัดสินใจรอบสอง

### คำตอบยืนยันรอบห้า

- Q28 OCR เติมยอด/วันเวลา/ธนาคาร/ผู้โอน/เลขอ้างอิง ให้ลูกค้าตรวจแก้ก่อนส่ง; ช่องอ่านไม่ชัดไม่เติมค่าที่แต่งขึ้น อ่านไม่ได้กรอกเองได้ และไม่ใช้ OCR ยืนยันธุรกรรมจริง
- Q29 ต้องการประมวลผลภายในระบบหากเป็นไปได้ และให้ประเมินทรัพยากร/ความคุ้มค่าก่อนเลือก; ไม่อนุญาต external OCR fallback โดยปริยาย
- Q30 เมื่ออนุมัติรายการโอนแม้บางส่วนแล้วล็อกแก้บิล; แก้บิลตุลาคมที่ไม่เคยอนุมัติได้ แต่ไม่คำนวณบิลอื่นที่ออกแล้วตามโดยอัตโนมัติ การเปลี่ยนจากบิลใช้กับบิลที่เลือกและเรทอนาคตของไซต์
- Q31 Owner/Accountant สร้างใบวางบิลเพิ่มเติม เลือกลูกค้าและไซต์เสมอ แยกประเภทจากบิลพลังงาน ไม่เปลี่ยนเรท
- Q32 เพิ่ม/แก้ไข/ลบรายการได้ แต่ละรายการมีรายละเอียด จำนวน ราคาต่อหน่วย และหมายเหตุ รวมยอดและเลือกโหมดรวม/ไม่รวมภาษีตามข้อเสนอ Q32 ที่ผู้ใช้ไม่ได้คัดค้าน รายละเอียดภาษีจริงยังไม่ได้กำหนด
- Q33 ตั้งภาษีกลางให้ผู้รับผิดชอบบัญชียืนยันก่อนใช้และ snapshot ต่อเอกสาร ยังไม่มีอัตรา VAT/กติกาหัก ณ ที่จ่ายที่ได้รับการยืนยัน ห้ามถือว่าเป็น 7% จาก reference
- Q34 manual bill เติมกำหนดชำระจากไซต์และแก้วันที่ได้ ออกแล้วส่งอีเมล พร้อม preview ก่อนออก ใช้ payment/receipt/reminder flow เดียวกัน

### ข้อกำหนดความถูกต้องที่เกิดจากการอนุมัติแยกรายการ

แยกสถานะรับรองรายการโอนจากสถานะชำระครบของบิล; ใช้ transaction/row lock ป้องกันอนุมัติซ้ำ ยอดเกิน และออกใบเสร็จซ้ำ เมื่อมี approved transfer ล็อกการแก้ยอด/เรททันที ทั้ง UI และ API; pending evidence ก็พักแก้ตาม Q19 ต้องไม่เรียก approved partial transfer ว่า paid invoice

### OCR discovery และเกณฑ์ประเมิน

พบ target comment 2 vCPU/4 GiB ใน compose แต่ไม่มีหลักฐานว่าเป็นเครื่องจริงปัจจุบัน ผลเดิมบนเครื่องพัฒนาหรือ Docker ไม่แทน target sizing ต้องสอบถาม CPU/RAM และจำนวนหลักฐานต่อวัน/พร้อมกัน จัด research แยกที่ docs/ocr-local-feasibility-2026-10-09.md

การออกแบบเบื้องต้น: queued OCR worker ภายใน ไม่ทำ inference ใน API request; เก็บหลักฐานต้นฉบับและค่าที่อ่านได้แยกค่าที่ลูกค้าแก้; status queued/processing/ready/failed; manual entry ใช้ได้เสมอ ไม่บังคับรอ OCR; no external fallback; benchmark field accuracy, p95 latency, peak RSS, CPU และผลกระทบ telemetry/API ก่อนเลือกรุ่นและ resource limit

### คำตอบยืนยันรอบสี่และขอบเขตเพิ่มเติม

- Q21 หน้าตรวจหลักฐาน desktop แสดงภาพ/PDF ซูมได้คู่ข้อมูลบิล/รายการโอน/ประวัติ; mobile เรียงแนวตั้ง พร้อมอนุมัติ/ปฏิเสธและ preview ใบวางบิลในหน้า ลูกค้าต้องแนบภาพแล้วแปลงเป็น text อัตโนมัติ รายละเอียด OCR และการยืนยันค่าก่อนส่งอยู่รอบถัดไป
- Q22 ตรวจรายการโอนแยกกัน เก็บรายการที่ผ่านไว้ ปิดชำระและออกใบเสร็จเมื่อยอดผ่านตรวจครบยอดบิล หากขาด/เกินแสดงส่วนต่างโดยยังไม่ปิดบิล
- Q23 ลูกค้าระบุยอด วันเวลาโอน ธนาคารต้นทาง เลขอ้างอิงถ้ามี และหลักฐาน เจ้าหน้าที่เห็นผู้ส่ง/ประวัติ ปฏิเสธมีเหตุผลและแจ้งในระบบ/อีเมล พร้อมส่งหลักฐานใหม่ ไม่ใช้ OCR อนุมัติการชำระโดยอัตโนมัติ
- Q24 ใบวางบิลมีผู้วางบิล/ผู้รับวางบิล ใบเสร็จมีผู้รับเงิน ตั้งชื่อ/ตำแหน่งได้; ผู้วางบิลอัปโหลดลายเซ็นเพื่อแนบอัตโนมัติได้ หากไม่มีเว้นช่องลงนาม เก็บลายเซ็นใน snapshot เอกสารแต่ละฉบับ
- Q25 ชื่อเมนู “ใบเสร็จรับเงิน” แต่เอกสารเป็นใบเสร็จรับเงิน/ใบกำกับภาษีเต็มรูปแบบ ไม่ใช่เอกสารภาษีแยกตามข้อเสนอรอบก่อน รายละเอียดภาษีและข้อมูลบัญชียังต้องยืนยัน ไม่ใช้ VAT ใน PDF ตัวอย่างเป็นข้อกำหนด
- Q26 ต้องเตือนก่อนแทนที่เรทอนาคต พร้อมแสดงรายการที่กระทบ; เรทใหม่ไม่มีวันสิ้นสุดและเก็บประวัติเรทเก่า
- Q27 ห้ามแก้เอกสารที่อนุมัติการชำระแล้ว แก้ได้เฉพาะรายการที่ยังไม่มีการอนุมัติการชำระ ผู้ใช้กล่าวว่า “แก้ย้อนหลังไม่ได้” พร้อมเงื่อนไขนี้ จึงต้องยืนยันว่าหมายถึงห้ามย้อนหลังข้ามบิล หรือห้ามเฉพาะบิลที่ชำระอนุมัติแล้ว โดยไม่ยกเลิก Q9 เรื่องแก้รอบตุลาคมเงียบ ๆ
- เพิ่ม manual billing: เลือกลูกค้า กรอกข้อมูล/จำนวนเงิน/หมายเหตุ และคำนวณภาษีอัตโนมัติ สำหรับเรียกเก็บเพิ่มเติม ต้องกำหนดไซต์ ผู้มีสิทธิ์ ฐานภาษี เลขเอกสาร วันครบกำหนด และวงจรชำระร่วมกับบิลอัตโนมัติ

### Frontier รอบห้า

Q28 OCR เติมฟิลด์และให้ตรวจทานก่อนส่งหรือส่งอัตโนมัติ; Q29 อนุมัติรายการโอนบางส่วนแล้วล็อกแก้บิลหรือไม่ และขอบเขตการแก้ข้ามบิล; Q30 manual billing ผูกไซต์และผู้มีสิทธิ์ออก; Q31 รูปแบบรายการและจำนวนเงินรวม/ไม่รวมภาษี; Q32 VAT/หัก ณ ที่จ่าย/ผู้มีอำนาจยืนยันข้อมูลภาษี; Q33 วันครบกำหนด/ส่งอีเมลของ manual billing; Q34 ผู้มีสิทธิ์ upload/use ลายเซ็นและ default signer

### คำตอบยืนยันรอบสามและขอบเขตเอกสารเพิ่มเติม

- Q16 Owner บันทึกแล้วออกใบวางบิลฉบับแก้ไขและส่งทันที ไม่ต้องมีผู้อนุมัติอีกคน; เก็บฉบับเดิมและ actor/reason/ยอดก่อนหลัง เป็นข้อยกเว้นแทนกติกาเดิมเรื่อง separate financial approver สำหรับการแก้เรทใบวางบิลที่ยังไม่ชำระเท่านั้น
- Q17 เรทใหม่มีผลต่ออนาคตแบบไม่กำหนดวันสิ้นสุด ปิดช่วงเก่าและเพิ่มช่วงใหม่อัตโนมัติ; การจัดการเรทอนาคตที่ตั้งรอไว้และบิลอื่นที่ออกแล้วเป็นกรณีขอบที่ยังต้องถาม

### Frontier รอบสี่: การตรวจหลักฐานและเอกสาร

| 4 ลบเมนูสัญญา | ไม่มีเมนูสัญญาในจุดนำทางที่ตกลง | ตรวจ sidebar/mobile/link/หน้าตรง; รักษาประวัติสัญญาและข้อมูลที่การคิดบิลใช้; ตัดสินใจว่าจะย้ายการจัดการไปหน้าไซต์หรือตั้งค่าบิล |
| 5 Admin ไม่เห็นเอกสาร | กำหนดขอบเขตการเงินของ Admin ใหม่ | ระบุทั้งหน้าแรก เมนู notification รายการ detail PDF และ API; แยก “ซ่อนเมนู” กับ “ไม่มีสิทธิ์” โดยไม่ใช้ frontend เป็นตัวคุมสิทธิ์เพียงอย่างเดียว |
| 6 Alert เงื่อนไขและผู้รับ | แจ้งในระบบและอีเมลตาม rule | ขอบเขตไซต์/อุปกรณ์/ค่าข้อมูล, operator, threshold, ระยะเวลาที่ผิดเงื่อนไข, ผู้รับ, cooldown, recovery; เก็บเหตุการณ์และผลส่งแยกช่องทาง; ไม่เปิดข้อมูลนอกสิทธิ์ผู้รับ |
| 7 Title โรงเรียน | ผู้ใช้รู้ว่ากำลังดูไซต์ใด | แสดงชื่อลูกค้า + ชื่อ/รหัสไซต์อย่างสม่ำเสมอ; หนึ่งลูกค้าหลายไซต์ต้องไม่กำกวม; เปลี่ยนไซต์แล้วไม่แสดงข้อมูลไซต์เก่าค้าง |
| 8 รอบบิลและ Config แบบ Display field | อ่านค่าที่มีผลใช้งานได้ | แสดงรอบ วันครบกำหนด และค่า config พร้อมหน่วย/วันที่มีผล/ที่มาค่า; จำกัดรายละเอียดเทคนิคตาม role; ค่าที่ไม่มีใช้สถานะไม่มีข้อมูล |
| 9 ตารางเอกสาร | วันที่ รายการบิล สถานะ ข้อมูล ยอดเงิน เรท และดาวน์โหลด | หนึ่งแถวอ้างรอบบิลชัดเจน; เรทหลายช่วงเปิดรายละเอียดได้; ปุ่มใบวางบิล/ใบเสร็จตามเอกสารจริงและสิทธิ์; ต้นฉบับไม่มีต้องไม่สร้างย้อนหลังจาก config ปัจจุบัน; รองรับมือถือ |
| 10 สถานะชำระ | อัปโหลดแล้วรอตรวจสอบ อนุมัติแล้วชำระแล้ว | แยกสถานะเอกสาร/การชำระ/การส่ง; ปฏิเสธหลักฐานและส่งใหม่ได้ตามกติกา; อนุมัติซ้ำ/พร้อมกันไม่เกิดใบเสร็จซ้ำ; audit ผู้ตรวจ เวลา เหตุผล |
| 11 ตั้งค่าตารางอัตราค่าไฟ | หน้าตั้งค่าระบบและช่วงวันที่มีผล | แยกเรทขายตามช่วงวันที่จาก TOU ตามชั่วโมง ถ้าต้องการทั้งสองต้องมีแบบจำลองแยก; ระบุขอบเขตกลาง/ลูกค้า/ไซต์และสิทธิ์; ไม่มีช่วงซ้อนหรือช่องว่างที่ทำให้คิดบิลผิด |
| 12 เปลี่ยนเรทเพิ่ม row อัตโนมัติ | เปลี่ยนครั้งเดียวแล้วใช้ต่อได้ | เพิ่ม rate version พร้อม effective date และปิดช่วงเก่าใน transaction; เก็บคนแก้/เหตุผล; ระบุว่าส่งผลต่อข้อมูลใด; ห้ามแก้ทับประวัติที่เอกสารออกแล้วอ้างอยู่ |
| 13 ออกบิลและแก้เรทหลังออก | วงจรออกบิลที่ชัดเจนพร้อม audit | ตัดสินใจ auto-issue หรือ draft-review และเวลารัน; เรทเปลี่ยนกลางรอบต้องแบ่งพลังงานตามช่วงจากข้อมูลจริง; เอกสารออกแล้วใช้ revision/cancel/reissue หรือ adjustment ตามกติกาที่ตกลง; คุมหลักฐานที่กำลังตรวจและการแก้พร้อมกัน |
| 14 ทวงบิล | ตั้งวันเริ่มเรียกเก็บและทุกกี่วัน | ระบุวันครบกำหนด/วันเริ่มทวง/ความถี่/เวลา/ผู้รับ; หยุดเมื่อจ่ายครบหรือยกเลิก; กติกาเดิมพักเมื่อหลักฐานรอตรวจ; ส่งซ้ำไม่ซ้ำเหตุการณ์และ retry มีขอบเขต |
| 15 Dashboard การผลิต/การเงิน | เข้าใจพลังงานและสถานะเงินได้ | แยกกำลังไฟ kW จากพลังงาน kWh และยอดเรียกเก็บจากยอดชำระ; แสดงช่วงข้อมูล/ล่าสุด/ไม่ครบ; สถานะเอกสารและการชำระสอดคล้องกับหน้ารายละเอียด |
| 16 เลือกไซต์เห็นไซต์/Gateway/Config | บริบทที่เลือกครบถ้วน | summary ลูกค้า/ไซต์/อุปกรณ์/การเชื่อมต่อ/config แสดงตามสิทธิ์; อ่าน config ที่มีผลจริง; ค่า sensitive ไม่เผยแพร่ในหน้าอ่านข้อมูล |
| 17 Register ตามรุ่น | แต่ละค่ามี Register Address ที่ถูกต้อง | ผูกผู้ผลิต/รุ่น/เวอร์ชัน profile; address/count/function/data type/endianness/scale/unit; ตรวจ address convention; JSON path สำหรับ payload เป็นคนละแนวคิดกับ Modbus address; เก็บ override รายอุปกรณ์โดยไม่แก้รุ่นกลาง |

## ลำดับดำเนินงานที่เสนอ

1. ตกลงศัพท์ สิทธิ์ และวงจรบิล: role matrix, site setup ownership, ความหมายตารางเรท, ออกบิล/แก้เอกสาร; บันทึก glossary เฉพาะคำที่ตกลงและ ADR เฉพาะ trade-off สำคัญ
2. ฐานข้อมูลและ API: เปลี่ยน schema แบบรักษาข้อมูลเก่า, rate history, audit, recipient selection, สถานะและ transaction; ตรวจ migration รวมถึงข้อมูลกำลังใช้งาน
3. ลูกค้าและ flow ไซต์/เกตเวย์: ทำสิทธิ์ server ก่อนเมนูและหน้าจอ; ใช้ configuration/register profile เดิมที่เหมาะสม; ตรวจว่าไซต์พร้อมคิดบิลเมื่อใด
4. ระบบเรทและเอกสาร: การแบ่งช่วงคำนวณ, snapshot, ตารางเอกสาร, หลักฐานและการอนุมัติ, การแก้เอกสาร; วงจรนี้เป็น prerequisite ของ job อัตโนมัติ
5. งานเบื้องหลังและ Alert: schedule เวลาไทย, locks/idempotency, outbox/retries, monitoring, ทวงบิลและ rule alerts; ทดสอบช่องทางจริงแยกจาก fixture
6. Dashboard และการรับงาน: ใช้ API/สถานะที่ยืนยันแล้ว, ทดสอบทุก role ข้ามไซต์และมือถือ; ซ้อม workflow ตั้งแต่สร้างลูกค้าจนดาวน์โหลดใบเสร็จ

## ชุดตรวจรับที่ต้องผ่าน

- Role matrix ครอบคลุมเมนู หน้าตรง API ไฟล์ดาวน์โหลด ผู้รับแจ้งเตือน และข้อมูลข้ามลูกค้า
- เปลี่ยนไซต์/สลับ Table-JSON โดยไม่สูญค่าหรือค้างข้อมูลของไซต์เดิม; JSON ไม่ถูกต้องไม่บันทึก
- รุ่นอุปกรณ์ต่างกันใช้ mapping ถูกต้อง และ override ไม่เปลี่ยนอุปกรณ์อื่น
- เรทใหม่กลางเดือน/ข้ามเดือน/วันสิ้นสุดแบบ inclusive; เรทซ้อน; ข้อมูลมิเตอร์ขาด; ไม่ประเมินพลังงานขึ้นเอง
- ออกบิลซ้ำ รัน job ซ้ำ ระบบหยุดระหว่าง transaction และ recovery ไม่สร้างเลข/เอกสาร/อีเมลซ้ำ
- อัปโหลด → รอตรวจสอบ → ปฏิเสธ/ส่งใหม่ → อนุมัติ → ชำระแล้ว → ใบเสร็จ พร้อม audit และไฟล์เดิม
- เปลี่ยนเรทไม่แก้ยอดของเอกสารประวัติ; การแก้เอกสารใช้กติกาอนุมัติที่ยืนยัน
- ทวงบิลตามกำหนดและหยุด/พักตามสถานะ; อีเมลล้มเหลวไม่ถูกแสดงว่าส่งสำเร็จ
- หน้าจอภาษาไทย/อังกฤษ desktop/mobile light/dark; ตารางเอกสารอ่านได้และปุ่มดาวน์โหลดตรงเอกสารจริง
- แยกผลตรวจโค้ด, automated tests, local integrations และ production verification ให้ชัด

## Design tree และข้อรอตัดสินใจรอบแรก

- A สิทธิ์: ความหมาย Admin ไม่เห็นเอกสาร → API/notification/dashboard visibility; ผู้สร้างไซต์ → ฟิลด์และสถานะส่งต่อ; ลบเมนูสัญญา → จุดจัดการข้อมูลที่ยังใช้คิดบิล
- B อัตราค่าไฟ: ช่วงวันที่หรือ TOU → ขอบเขตกลาง/ลูกค้า/ไซต์ → inheritance และการเปลี่ยนกลางรอบ
- C วงจรบิล: auto-issue หรือ review → เวลารัน → การเปลี่ยนเรทในเอกสารค้างชำระ → การอนุมัติและ revision
- D Alert: ประเภทกฎและขอบเขตผู้รับ → debounce/cooldown/recovery → ช่องทางและ retry
- E อุปกรณ์: source ของรุ่นและ protocol → profile version/address convention → validation และ rollout

คำถามรายละเอียดที่ขึ้นกับคำตอบรอบแรกจะถามในรอบถัดไป ไม่ถือว่าค่าแนะนำเป็นคำตอบที่อนุมัติ
