# ข้อมูลเชื่อมต่อ Gateway — Solar staging

วันที่: 30 กันยายน 2569 · ฉบับร่าง 0.1

**สถานะ: ร่างสำหรับตกลงการเชื่อมต่อ ยังไม่เปิดรับข้อมูล**

เอกสารนี้จัดทำให้ผู้จัดการ Gateway ตรวจสอบว่าตัวอุปกรณ์สามารถส่งข้อมูลตามรูปแบบที่ระบบรองรับได้หรือไม่ ก่อนนัดเชื่อมต่อจริง เริ่มทดลอง 1 Gateway แล้วค่อยขยายจำนวน โดยเก็บข้อมูลจริงต่อเนื่องและแยกจากข้อมูลทดสอบอัตโนมัติ

## 1. ข้อมูลการเชื่อมต่อ

| รายการ | ค่าหรือสถานะ |
|---|---|
| เว็บสำหรับดูข้อมูล | https://solar.nateekarn.dev — ชื่อที่เลือกไว้ ยังไม่ยืนยันว่าเปิดใช้งานแล้ว |
| MQTT hostname | mqtt-solar.nateekarn.dev — ชื่อที่เลือกไว้ ยังไม่ยืนยัน DNS และการเชื่อมต่อ |
| วิธีส่งข้อมูล | MQTT; รูปแบบข้อความ JSON |
| การเข้ารหัส | เสนอใช้ MQTT ผ่าน TLS; ต้องยืนยันว่า firmware รองรับและทดสอบ certificate ก่อนใช้งาน |
| Port | รอทีมระบบแจ้งหลังตั้งค่าและทดสอบ; ยังไม่มี port ที่ยืนยันพร้อมใช้ |
| MQTT version | รอยืนยันร่วมกับ firmware และ broker ที่ตั้งค่าจริง |
| Username / Password | ทีมระบบจะสร้างสำหรับ Gateway นี้และส่งแยกผ่านช่องทางที่ตกลงกัน |
| Gateway name / Device serial | รอข้อมูลจริงและลงทะเบียนในระบบ |
| วันเริ่มส่งข้อมูล | รอนัดหลังทดสอบเชื่อมต่อและบันทึกข้อมูลชุดแรกผ่าน |

บัญชี MQTT สำหรับอุปกรณ์เป็นคนละบัญชีกับบัญชีเข้าเว็บ ระบบรับข้อมูลจาก Gateway ผ่าน MQTT ในรอบนี้ ยังไม่มี HTTP POST สำหรับรับ telemetry ที่เปิดใช้งาน

## 2. ช่องทางส่งและรับข้อความ (Topic)

ทีมระบบจะส่งชื่อ topic จริงหลังลงทะเบียน Gateway ตัวอย่างต่อไปนี้ใช้ชื่อสมมติ `PILOT-GW-001`:

| หน้าที่ | Topic ตัวอย่าง | ฝั่ง Gateway |
|---|---|---|
| ส่งข้อมูลมิเตอร์ | energy/PILOT-GW-001/telemetry | Publish |
| รับการยืนยันบันทึกข้อมูล | energy/PILOT-GW-001/response | Subscribe |
| รับค่าตั้งจากระบบ | energy/PILOT-GW-001/config | Subscribe |

- ตัวพิมพ์และเครื่องหมาย `/` ต้องตรงกับที่ทีมระบบแจ้ง
- ตัวอย่างนี้ใช้รูปแบบ `energy/{gatewayName}/...`; อย่านำ Site ID มาแทน Gateway name
- ข้อเสนอสำหรับ telemetry: QoS 1 และ retain=false; ต้องยืนยัน firmware และตั้งค่าสิทธิ์ก่อนเชื่อมต่อจริง
- ระบบส่ง response ด้วย QoS 1 และไม่ตั้ง retain ส่วน config ใช้ QoS 1 และ retain=true
- ให้ subscribe response ก่อนเริ่มส่งข้อมูล เพื่อรับการยืนยันของแต่ละชุด
- สิทธิ์ที่เสนอ: อุปกรณ์ส่งได้เฉพาะ telemetry ของตนเอง และอ่านได้เฉพาะ response/config ของตนเอง ไม่ใช้สิทธิ์ครอบคลุม Gateway อื่น

## 3. รูปแบบข้อมูลที่เสนอสำหรับเริ่ม Pilot

เริ่มด้วยค่าที่ Gateway แปลงหน่วยแล้ว (decoded metrics) หนึ่งข้อความต่อหนึ่งมิเตอร์และหนึ่งเวลาที่วัด ไม่ส่งเป็น array รวมหลายมิเตอร์

```json
{
  "ingestionId": "PILOT-GW-001-METER-001-20260930T030000Z-000001",
  "serialNumber": "PILOT-METER-001",
  "sourceTime": "2026-09-30T03:00:00.000Z",
  "metrics": {
    "voltage": 230.81,
    "current": 4.4,
    "activePower": 1000,
    "apparentPower": 1015.56,
    "reactivePower": 177.1,
    "frequency": 50,
    "powerFactor": 0.9847,
    "totalEnergy": 12345.67
  }
}
```

**ตัวอย่างนี้ใช้ serial และเวลาสมมติ จึงยังส่งทดสอบกับระบบจริงไม่ได้** ก่อนทดสอบต้องเปลี่ยนเป็น serial ที่ลงทะเบียนและเวลาที่วัดจริง การส่งซ้ำของข้อมูลชุดเดิมต้องเก็บ ingestionId และ sourceTime เดิม

| Field | ความหมายและข้อกำหนด |
|---|---|
| ingestionId | รหัสประจำข้อมูลชุดนี้ แนะนำให้มีทุกข้อความและไม่ซ้ำกับชุดใหม่ ใช้ค่าเดิมทุกครั้งที่ส่งชุดเดิมซ้ำ |
| serialNumber | serial มิเตอร์ที่ลงทะเบียนตรงกันในระบบ; อีกทางเลือกคือ deviceId ที่ทีมระบบออกให้ ให้ตกลงใช้แบบเดียวใน Pilot |
| sourceTime | เวลาที่วัดจริง แนะนำ ISO 8601 แบบ UTC ลงท้าย Z เช่นตัวอย่าง ไม่เปลี่ยนเป็นเวลาส่งย้อนหลัง |
| metrics | ค่าที่วัดได้จริง เป็นตัวเลข JSON ไม่ใช่ข้อความตัวเลข ต้องมีค่าที่ระบบรองรับอย่างน้อยหนึ่งค่า |

ไม่จำเป็นต้องส่ง gatewayId หรือ siteId ในรูปแบบที่เสนอนี้ หากส่งต้องใช้ ID จริงจากระบบ ห้ามใช้ชื่อสมมติแทน UUID เพราะจะไม่ผ่านการจับคู่อุปกรณ์

### หน่วยของค่าที่วัด

| Field | หน่วย |
|---|---|
| voltage | V |
| current | A |
| activePower | W |
| apparentPower | VA |
| reactivePower | var |
| frequency | Hz |
| powerFactor | ไม่มีหน่วย |
| totalEnergy | kWh สะสมตามค่ามิเตอร์ ไม่ใช่พลังงานเฉพาะช่วงเวลานั้น |

- ค่าที่ไม่มีให้ละ field หรือส่ง null ห้ามแทนด้วย 0 หากไม่ได้วัดว่าเป็นศูนย์จริง
- ห้ามส่ง NaN, Infinity หรือค่าตัวเลขในเครื่องหมายคำพูด
- ถ้าอุปกรณ์มี activePower หน่วย kW ให้แปลงเป็น W ก่อนส่งตามรูปแบบข้างต้น หรือใช้ activePowerKw โดยตกลงรูปแบบเดียวกันก่อน ห้ามส่งค่าหลาย field ที่ขัดแย้งกัน
- นาฬิกา Gateway ต้องตรง: โค้ดปัจจุบันปฏิเสธเวลาที่ล่วงหน้ากว่าเวลารับเกิน 30 วินาที
- ข้อมูลย้อนหลังรับได้เมื่อผ่านข้อกำหนดอื่น แต่ข้อมูลอายุเกิน 120 วินาทีจะไม่แสดงว่าเป็นข้อมูลสด; หากเวลาอยู่ในอนาคตเล็กน้อยแต่ยังผ่านการรับ ก็ยังไม่ถือว่าเป็นข้อมูลสดจนถึงเวลานั้น
- ขอให้ยืนยันว่า totalEnergy คือพลังงานสะสมชนิดใดของมิเตอร์ เช่น import/export พร้อมพฤติกรรมตอนรีเซ็ตหรือเปลี่ยนมิเตอร์ เพื่อให้เลือกค่าตรงกับงานระบบ

## 4. การยืนยันรับข้อมูลและการส่งซ้ำ

ระบบส่งข้อความบน response หลังทำรายการบันทึกข้อมูลสำเร็จแล้ว ตัวอย่างรูปแบบ response:

```json
{
  "status": "acknowledged",
  "gateway": "PILOT-GW-001",
  "deviceId": "11111111-1111-4111-8111-111111111111",
  "ingestionId": "PILOT-GW-001-METER-001-20260930T030000Z-000001",
  "sourceTime": "2026-09-30T03:00:00.000Z",
  "serverReceivedAt": "2026-09-30T03:00:01.000Z",
  "duplicate": false
}
```

UUID และเวลาใน response นี้เป็นตัวอย่างเท่านั้น deviceId ใน response เป็น UUID ของมิเตอร์ในระบบ แม้ข้อความขาเข้าจะระบุ serialNumber

1. Gateway เก็บข้อมูลชุดที่ยังไม่ได้รับ response ไว้ก่อน
2. เมื่อได้ status=acknowledged ที่ตรงกับ ingestionId, sourceTime และอุปกรณ์ จึงถือว่าระบบยืนยันชุดนั้นแล้ว
3. หาก response ไม่ถึง Gateway ให้ส่งข้อมูลชุดเดิมซ้ำโดยคง ID, เวลา และค่าที่วัดเดิม
4. duplicate=true หมายถึงระบบพบว่าข้อมูลชุดนี้บันทึกไว้แล้ว จึงยืนยันได้เช่นกัน
5. ข้อความตอบรับระดับ MQTT หรือ PUBACK เพียงอย่างเดียว ยังไม่ใช่หลักฐานว่าข้อมูลถูกบันทึกในระบบ Solar แล้ว

หากอุปกรณ์ไม่รู้จัก, topic ไม่ตรง, รูปแบบข้อมูลไม่ผ่าน หรือบันทึกไม่สำเร็จ อาจไม่มี application response กลับมา จึงไม่ควรรอข้อความ error เสมอไป ให้เก็บข้อมูลและแจ้งทีมระบบเพื่อตรวจสอบ

ระยะเวลารอ response, รอบส่งซ้ำ, การหน่วงระหว่าง retry, จำนวนข้อมูลที่เก็บขณะ offline และความเร็วส่งย้อนหลัง ยังต้องตกลงก่อนเริ่มจริง เพื่อไม่ให้เกิดการส่งซ้ำถี่จนรบกวนระบบ

## 5. กรณี Gateway ส่งค่า Register ดิบ

ระบบมีเส้นทางถอดรหัสผ่าน registers หรือ rawRegisters แต่ต้องลงทะเบียนตารางแปลงค่าของมิเตอร์ให้ตรงก่อน จึงขอข้อมูลจากทีม Gateway ดังนี้:

- ยี่ห้อ รุ่น และคู่มือ register ของมิเตอร์
- ตัวอย่าง JSON จริงที่อ่านได้ พร้อมค่าหน้าจอมิเตอร์ในเวลาเดียวกัน
- ชื่อ key/address ของ register และรูปแบบการนับ address
- ชนิดข้อมูล, scale, หน่วย, byte order และ word order

แต่ละ register word ต้องเป็นจำนวนเต็ม 0–65535 และต้องมี mapping ที่มีผล ณ เวลาที่วัด หากส่งทั้ง registers และ metrics ระบบปัจจุบันจะใช้ค่าจาก registers จึงแนะนำให้เลือกหนึ่งรูปแบบต่อข้อความและยืนยัน fixture ที่รู้คำตอบก่อนเริ่ม

## 6. ค่าตั้งที่ส่งจากระบบไป Gateway

ระบบสามารถส่ง pollingIntervalSeconds และ alertRules ผ่าน config topic โดยเก็บข้อความล่าสุดไว้ที่ broker การ publish สำเร็จยืนยันเพียงว่าข้อความไปถึง broker ไม่ได้ยืนยันว่า firmware นำค่าไปใช้แล้ว

รอบ Pilot ให้ยืนยันก่อนว่า firmware อ่านและใช้ค่าตั้งนี้ได้หรือไม่ หากยังไม่รองรับ สามารถตกลงตั้งช่วงเวลาส่งข้อมูลที่อุปกรณ์ก่อน โดยไม่ถือว่าการส่ง config สำเร็จคืออุปกรณ์เปลี่ยนค่าจริง

## 8. ขั้นตอนเริ่มส่งจริง

1. ตกลงรูปแบบและตรวจตัวอย่างข้อมูลร่วมกัน
2. ทีมระบบ deploy, ตั้ง DNS/TLS, สร้างบัญชีและลงทะเบียนอุปกรณ์ แล้วส่ง connection sheet ที่มีค่าจริง
3. เชื่อมต่อ ส่งหนึ่งชุด รับ application response และตรวจว่าค่าถูกบันทึกและแสดงบนเว็บตรงกับข้อมูลที่ส่ง
4. เปิดรับข้อมูล Pilot และตรวจการส่งซ้ำ การหลุด/ต่อใหม่ และความต่อเนื่องของข้อมูลต่อไป

ไม่ต้องรอทดสอบต่อเนื่อง 24 ชั่วโมงเพื่อส่งเอกสารร่างนี้ แต่จะยังไม่แจ้งว่า endpoint พร้อมใช้งานจนกว่าการตรวจสั้นในข้อ 3 จะผ่าน การทดสอบข้อมูลจำลองเบื้องต้นทำโดยทีมระบบก่อนนัดอุปกรณ์จริง
